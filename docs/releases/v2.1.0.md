# Scanly SDK v2.1.0

Status: release-qualified candidate. Registry publication and post-publication verification are tracked separately; this document is not a publication record.

## New: Link Intelligence

- Local URL risk analysis and IDN-aware canonicalization.
- Threat-intelligence provider abstraction, optional Google Web Risk and lookup-only VirusTotal.
- Hardened server-only remote inspection with DNS/IP pinning, bounded responses and per-hop redirect validation.
- Provider-neutral, JSON-schema-validated LLM-assisted phishing/scam interpretation.
- Deterministic risk engine with threat-authority precedence and bounded AI contribution.
- Explicit privacy modes, hashed cache, single-flight deduplication and lifecycle cancellation.
- Browser/server separation and an optional self-hosted demo endpoint.

## Privacy

Barcode decoding remains local. URL network analysis is opt-in. No barcode image/frame is sent to AI providers. Query values are redacted from display URLs and AI evidence; exact reputation lookups and destination inspection may need full URLs and require consent.

## Security

Remote URL inspection uses SSRF controls. LLM output is advisory. Threat-intelligence authority cannot be overridden by AI. No verdict guarantees safety. Production deployments need isolated egress, shared rate limits and an explicitly configured LLM transport; the stock demo does not invent an AI result when no provider is configured.

## Compatibility

Existing v2 scanner APIs remain compatible. URL intelligence is an independent, default-disabled module, not part of decoder scheduling. Native version metadata advances with the release line; Native build/signing/artifact qualification must be repeated before publication. Existing Native evidence is not rebranded as 2.1.0 evidence.

## Qualification

All software, browser, API/package, security, Native, SBOM/license, artifact/reproducibility, signing and publication gates must pass on the final release identity. Feature-branch test results are development evidence only. See [URL safety architecture](../url-safety.md) and the candidate qualification record when available. Issue #13 remains independent.

The Stable manifest generator refuses new-version generation without `STABLE_QUALIFICATION_RECORD`: an exact-source `scanly-release-qualification-1` record with version, sourceCommit, sourceTree and content-addressed PASS evidence (`path`, `sha256`, `sourceCommit`) for software, apiAbi, security, sbom, licenses, native, npmReproducibility, signing, publicationCredentials and deployment. Fresh public signing metadata and two independent npm build/hash maps are required. Legacy 2.0.x GO/credential/reproducibility claims cannot be inherited.

For the new `@scanly/url-safety` package only, the qualified first-publication path uses npm's official `--provenance-file` support: exact release tarball bytes carry a GitHub-hosted build's verified Sigstore provenance, while an authenticated owner completes npm's interactive 2FA locally. No npm credential is sent to CI, no placeholder version is published, and no provenance or signing requirement is waived. Existing packages continue using their verified OIDC workflow. Dependencies publish before the new package; a deferred bootstrap is reported as incomplete, never as full release success. The new package's Trusted Publisher can be initialized after its first genuine release.

### Additive provenance compatibility correction

The first Registry submission was rejected with E422: although the original Sigstore signatures and artifact subjects verified cryptographically, npm requires `resolvedDependencies[0]` to match the GitHub certificate's source repository ref and commit. The original bundles listed the separately checked-out product source first. The rejected submission did not publish the new package.

[The additive recovery record](../../release/stable/v2.1.0/v2.1.0-provenance-recovery.json) preserves this failure and binds replacement proofs to two fresh independent GitHub-hosted builds. All 11 rebuilt tarballs match the frozen release byte-for-byte; all 22 replacement bundles are signature-, identity-, and subject-verified. The workflow source is now first and the exact product source remains a separate explicit dependency. The signed tag, original manifest, original provenance, and frozen artifacts remain unchanged.

Use `npm run stable:bootstrap -- --qualified-provenance-recovery` only with this verified additive record. The command rechecks the live successful workflow, both independent signed URL Safety bundles, exact artifact hashes, original qualification, and owner authentication before requesting publication. A completed build or local signature check is not proof of Registry acceptance; post-publication checks remain mandatory.
